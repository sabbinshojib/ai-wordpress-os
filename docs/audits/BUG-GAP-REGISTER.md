| LIKELY-001 | Medium | Security / REST | `src/Mcp/Transports/RestTransport.php::isLocalDevelopment()` | `require_https` is bypassed whenever `HTTP_HOST` contains `localhost`, `127.0.0.1`, `.local`, or `.test`. On a misconfigured reverse proxy / permissive default vhost, a client-supplied `Host` header could trigger this exemption on a production endpoint. | Exploitability depends entirely on hosting/proxy configuration not present in this repository; could not be tested against a real HTTP stack in this audit. | Prefer a server-side, non-client-controlled signal (e.g., `WP_ENVIRONMENT_TYPE` alone, or an explicit admin-configured allowlist) instead of trusting `HTTP_HOST`. | Add a unit test asserting `isLocalDevelopment()` returns false for a spoofed `Host` header when `WP_ENVIRONMENT_TYPE` is not `local`. |
| LIKELY-002 | Medium | Security / concurrency | `src/Security/RateLimiter.php::allow()` | Non-atomic transient read-increment-write; concurrent requests within the same window can each pass the check before any persists its increment. | The code's own comment acknowledges the tradeoff explicitly ("acceptable here because limits are protective, not billing-precise") — flagged as "likely" because real-world bypass magnitude depends on the object-cache backend and request concurrency, not verified under load in this audit. | If the rate limiter must ever be a hard ceiling (e.g., cost control), replace with an atomic primitive (`wp_cache_incr()` against a real external object cache, or a DB-level atomic counter). | Add a concurrency test that fires N parallel `allow()` calls against a mocked non-atomic transient store and asserts the over-limit count matches the known race window (documents the risk quantitatively rather than eliminating it, unless the fix above is also applied). |
| LIKELY-003 | Low | UI / release | `assets/js/admin-dashboard.js` vs. `build/dashboard-src/src/app.jsx` | No build-reproducibility check exists; cannot independently confirm the shipped minified bundle is the exact product of the current source without running `npm install && npm run build` (blocked by this audit's no-install policy). | Presumed in sync (single-commit baseline, both files added together) but unverified by execution. | Add a CI step that rebuilds the bundle from source and diffs it against the committed artifact (fails the build on drift), or stop committing the built artifact and build it at release-packaging time instead. | CI job, not a unit test. |

## Architecture gaps (expected at this phase — not bugs)

| ID | Gap | Why it's out of scope for Sprint 0.1 |
|---|---|---|
| ARCH-001 | No Transaction Engine / ChangeSet model | Explicitly a Phase-2+ roadmap item; Phase 1 is read-only + safe/approval-gated writes only. |
| ARCH-002 | No Snapshot/Diff/Rollback engine | Same as above; depends on ARCH-001. |
| ARCH-003 | No background job / async execution system | All tool execution today is synchronous within the HTTP request; acceptable at current tool complexity, will not scale to long-running Phase-2 operations (large content migrations, staging syncs). |
| ARCH-004 | No idempotency-key / replay protection for MCP `tools/call` | A retried mutating call (e.g., after a client timeout) can double-execute. Documented as a Phase-2-adjacent hardening item, not blocking Phase 1's own correctness. |
| ARCH-005 | No RBAC/team support beyond raw WordPress capabilities | `ai_os_use`/`ai_os_approve` capability constants are referenced but never granted to any role — works today only because `manage_options` also satisfies every gate. Real multi-approver workflows need this wired up. |
| ARCH-006 | No versioned API contract / deprecation strategy for the REST or MCP surfaces | Fine for a v1.0.0 baseline; becomes necessary the moment a breaking change is needed post-release. |
| ARCH-007 | No feature-flag system | All behavior is controlled by the single `Settings` mode/threshold model; adequate for Phase 1's scope. |
